name: review-diff
description: >
PR の diff を設計書と突き合わせてレビューする。「差分を設計書と照らし合わせて」
「PR を確認して設計書と比べて」「diff を読んで報告して」「次の順で読んで報告して」
のような依頼でトリガーされる。diff 取得・設計書読み込み・3ステップ分析・表形式報告
までを一気に行う。コードは直さない。Laravel プロジェクトで設計書（docs/design/\*.md）が
ある場合は必ずこのスキルを使うこと。

---

## 目的

PR の差分が設計書の意図から外れていないかを確認し、**人が判断すべき箇所を絞り込む**。
コードを直すのではなく、指摘だけを行うのがゴール。

---

## 入力

ユーザーから以下を受け取る（会話から読み取れる場合は確認不要）：

- **PR 番号**: `gh pr diff <N>` で差分を取得する
- **設計書パス**: `docs/design/`（`data.md`・`permissions-api.md`・`behavior.md`・`screens.md`・`acceptance.md` など）
- **触っていないはずのファイル一覧**: 設計書の「変えないもの」節から読み取る。ユーザーが明示した場合はそちらを優先する

---

## 手順

### Step 0: 情報収集（並行実行）

`gh pr diff <N>` と設計書の読み込みを **同時に** 実行する。両方揃ってから分析に進む。

### Step 1: 設計書との突き合わせ（書いていないものが増えていないか）

差分に含まれる変更が設計書の範囲に収まっているかを確認する。受け入れ条件は `acceptance.md`、画面は `screens.md`、テーブルは `data.md`、権限とAPIは `permissions-api.md` にある。

- **composer.json / package.json** の変更は外部依存の追加を意味するので最初に確認する
- 新規ファイルがすべて設計書の「増えるファイル」節に対応しているかを見る
- 差分の PR が設計書のどの機能に対応するかが一致しない場合は、先にその不一致を明記する

### Step 2: 触っていないはずのファイルの確認

設計書の「変えないもの」節に記載されたファイル・ルート・ロジックを対象にする。

- **削除行（`-` で始まる行）から先に確認する** — 意図しない削除は追加より見落としやすい
- 設計書に「変えない」と明記されているメソッド・ルートが実際に変わっていないかを見る

### Step 3: 中身を読む

以下の観点を順に確認する：

| 観点               | 何を見るか                                                                                                 |
| ------------------ | ---------------------------------------------------------------------------------------------------------- |
| N+1                | 一覧系クエリに `with()` Eager Loading が付いているか                                                       |
| 認可の置き場所     | `authorize()` / Policy の呼び出しが正しい位置にあるか。作成系は不要な場合もある（auth ミドルウェアで十分） |
| マスアサインメント | `create()` / `fill()` に渡す配列に外部入力が混入していないか。モデルの `$fillable` と照合できるか          |
| XSS                | Blade テンプレートで `{!! !!}` を使っていないか。`{{ }}` になっているか                                    |
| CSRF               | POST フォームに `@csrf` があるか                                                                           |
| 入力チェック       | バリデーションルールが設計書の仕様と一致しているか。エラーメッセージが日本語か                             |
| 書き方の揃い       | 既存コードのスタイル（インデント・命名・構造）と揃っているか                                               |

---

## 出力形式

**表**（1 行 1 観点）で報告する：

```
観点 | 判定 | ファイル名:行番号 | 気づいたこと
```

判定の選択肢：

| 判定       | 意味                            |
| ---------- | ------------------------------- |
| **OK**     | 問題なし                        |
| **要確認** | 人の目で確認が必要              |
| **対象外** | 差分に該当箇所がない / 判定不要 |

判定できない場合は「対象外」と書かず、「何が足りなくて判定できないか」を気づいたこと欄に書く（例：「Message モデルの `$fillable` が差分に含まれないため確認できない」）。

**最後に**、人が自分の目で読むべき場所を **3 つまで** 箇条書きで挙げる。
ファイル名:行番号を明示し、なぜそこを読むべきかを一言添える。

---

## 制約

- **コードは直さない**。指摘のみ行う
- 判定できないものを「OK」にしない。不明は不明と書く
